## 0. 核心判断

我们要做的不是学习工具、编程工具、聊天工具和笔记软件的并排集合，而是：

> **一个本地优先、模型可替换、具有连续记忆，能够使用工具、与人共同编辑并交付真实结果的通用个人 Agent。**

它的统一性不来自“只有一个页面”，而来自以下不变量：

1. **一个任务内核**：学习、编程、文档、决策都经历理解、行动、验证、交付和记录。
2. **一套资源身份**：文件移动、重命名、跨文件夹和跨项目不会抹掉它与历史的关系。
3. **一套产物版本**：代码、文档、表格、教案和计划都能 diff、共同编辑、验证、撤销和继续。
4. **一套连续记忆**：任务可以分视图，记忆不随模式和渠道分裂。
5. **一套权限与证据**：模型说“完成”不算完成，必须有相应领域的真实证据。
6. **一套个人化机制**：用户创造的模式只是能力、界面和自动化规则的组合，不是另一个孤立 Agent。
7. **一套主动行为规则**：定时和事件触发进入同一任务系统，可审批、可去重、可取消、可追踪。

“各取所长”在这里的含义是：

> **借鉴产生好体验的机制，同时修复它在原产品中的短板；不是复制界面、代码、产品边界和功能数量。**

## 1. 产品边界

### 1.1 三类用户，一套内核

| 用户 | 真正需要 | 在架构中的位置 |
|---|---|---|
| 普通用户 | 用自然语言办事；得到真实文件或结果；不用理解工具；不被欺骗、打扰或锁定 | 统一任务、编辑器、证据式完成、默认安全策略 |
| 当前用户 | 学习、编程项目、比赛与合作、文档、沟通、长期成长；中文优先；成本可控 | 用自己的场景组合出的一套长期用法，作为压力测试 |
| 其他个人用户 | 自学、开发、写作、创业、资料管理；自己的模型、数据和工作流 | 可替换模型、能力包、自定义场景、开放导出 |
| 开发者 | 可扩展工具和验证器；可检查运行过程；能复用底层而不必复制整个产品 | 能力注册、事件日志、确定性边界、版本化配置 |

当前用户的学习场景是**示例场景和压力测试**，不是写死在通用内核里的产品定义。

### 1.2 “通用”不等于什么

- 不等于内置所有软件和所有平台；
- 不等于企业多租户、团队协作平台；
- 不等于多 Agent 互聊；
- 不等于无限权限的全自动机器人；
- 不等于把全部历史塞进超长上下文；
- 不等于把所有功能交给用户自己装插件；
- 不等于为了“主动”而频繁发消息；
- 不等于导入 Claude Code、Codex、ChatGPT 的历史记忆。

多平台通信是新的输入输出渠道，不是跨工具记忆共享。

### 1.3 一个 Agent 不等于只有一条消息流

可以存在：

- 一个任务的主线与侧问；
- 不同时间的对话视图；
- 代码、文档、wiki、日程等不同工作视图；
- 同一任务在不同渠道的延续。

但它们不能各自拥有孤立状态。用户不应该因为从学习转到编程，就重新介绍自己、重新上传资料或复制前情。

## 2. 市场机制拆解：借什么，修什么

本节只保留会改变 PA 设计的结论。公开指标未独立复现的，不作为架构正确性的证据。

### 2.0 ChatGPT 与 OpenAI Dots：消费级个人 Agent 的真实状态

**ChatGPT 值得借鉴**

- 跨对话合成记忆（Dreaming V3）；
- 后台 consolidation，不占用户等待时间；
- 时间改写，把“准备去”改写成“去过”；
- 用户可见的 Memory Summary，可查看、编辑、删除；
- Projects、GPTs、Tasks、Connectors 把任务、资料和外部服务连起来。

**ChatGPT 的毛病**

- 记忆原地重写，旧版本不可回滚，迭代整理会漂移；
- 记忆是黑盒：看不到某次回答用了哪条记忆、哪段原话；
- 删除不等于立刻消失，存在保留窗口；
- 记忆不可迁移，导出对话不等于导出记忆语义；
- Chat / Projects / GPTs / Tasks / Codex / Connectors 多套模式，上下文、能力和额度不统一；
- 模型路由和降智不可见；
- 云优先，身份、记忆和历史不在用户手里。

**OpenAI Dots 值得借鉴**

- 常驻云端 Agent，有自己的电脑和浏览器；
- 可同时处理多个任务，支持子 Agent；
- 空闲时做主动研究；
- 可连接大量应用；
- 用户可随时观看执行过程，设置允许/阻止/需审批规则。

**OpenAI Dots 的毛病**

- 云端优先，执行环境、数据和记忆都在平台；
- 闭源模型，不可替换；
- 只对 Pro / Business 开放，部分市场不可用；
- 与 ChatGPT / Work / Codex 仍是多套模式；
- 主动研究只读，真正写入仍受限；
- 记忆与上下文不可审计；
- Agent 仍会犯错，且平台历史上出现过“欺骗行为”问题。

**我们的选择**

- 借：跨对话合成、用户可见摘要、常驻任务、主动研究、应用连接；
- 修：证据链、版本化、可迁移、本地身份、场景统一、模型可替换；
- 拒绝：云优先、不可审计、多套模式、订阅档位锁定。

### 2.1 Claude Code：共同编辑与可恢复性

**值得借鉴**

- IDE 自动附带当前文件和选区，减少手动描述上下文；
- 原生 diff 中逐块接受或拒绝；
- 用户可以直接修改 Agent 的提案，Agent 会收到“提案已被用户改过”的事实；
- 对话恢复与代码恢复可以分别选择，也可以一起恢复；
- checkpoint 随会话保存，重启后仍能尝试恢复。

**需要修复的短板**

- 官方明确说明：仅由 Bash 改动的文件不一定被 checkpoint 跟踪；外部并发修改、符号链接等也有恢复限制；
- checkpoint 不是长期版本系统；
- CLI 的项目体验容易把会话、配置和当前目录绑定。

**PA 的选择**

- 所有写路径都进入统一的产物版本机制，不能只监控编辑工具；
- 文件版本与对话版本分开，可组合回滚；
- 当前目录只是执行位置，不是任务和记忆的身份。

来源：[Claude Code IDE integrations](https://code.claude.com/docs/en/ide-integrations)、[Checkpointing](https://code.claude.com/docs/en/checkpointing)。

### 2.2 Codex：生产级执行底座与 focused diff

**值得借鉴**

- 进程内 agent loop、工具调度、审批、沙箱、线程和 rollout；
- IDE 中围绕当前文件和选区工作；
- focused diff、Undo、任务结束后回到同一对话复查；
- 动作分类审批和确定性 exec policy，而不是让模型自己判断命令是否危险。

**需要修复或避免的短板**

- coding-only 的记忆桶不能直接承担个人经历；
- 全量 crate 和云、多 Agent 等复杂能力不应为了“完整”而保留在默认路径；
- 项目目录不能成为所有历史关联的唯一键。

**PA 的选择**

继续复用现有进程内 Codex，不重写 agent loop；在其上补通用任务、资源、产物和长期记忆。

来源：本地源码拆解 `docs/03-research.md`；[Codex IDE](https://learn.chatgpt.com/docs/codex/ide)。

### 2.3 Pi：小内核、树状会话与用户可定义性

**值得借鉴**

- “Primitives, not features”：核心保持小，工作流由用户适配；
- 会话是树，分支保存在同一会话结构中，而不是复制出许多无关系对话；
- extensions、skills、prompt templates、themes 可组合成包；
- 扩展能注入动态上下文，模型和 provider 可替换；
- steering 与 follow-up 区分“立即影响当前工作”和“完成后处理”。

**需要修复的短板**

Pi 故意不默认内置很多能力。PA 不能把安全编辑、权限、恢复、任务状态等基本能力也推给用户自行扩展。

**PA 的选择**

- 小内核，但可信完成所需能力默认内置；
- 场景使用统一组合机制；
- 分支属于同一任务历史，不分叉出孤立记忆。

来源：[Pi 官方站点](https://pi.dev/)。

### 2.4 DSH：日志、装配和能力组合

**值得借鉴**

- append-only Session 事件日志，模型可见内容可审计；
- 模型历史从日志派生，不维护另一份容易不一致的历史；
- 稳定 Prompt Section、动态 Prompt Context、按范围提供工具；
- 工具有执行、展示、超时、取消和审计；
- compaction 是日志中的显式区间；
- Preset 是能力组合，不必成为割裂的产品模式。

**需要避免**

- Electron 运行时；
- 一切皆插件和插件市场带来的核心复杂度；
- 把动态记忆放进稳定前缀，破坏缓存。

**PA 的选择**

借日志、装配、工具展示投影和 Preset；保持 Rust 单进程与少量内置能力。

来源：本地 `research/deepseek-harness` 与 `docs/03-research.md`。

### 2.5 OpenClaw：统一通信入口与持久自动化

**值得借鉴**

- 本地 Gateway 统一会话、工具、事件和渠道；
- 不同聊天平台是 channel，不是不同 Agent；
- 外部发送者默认不可信，需要配对和权限边界；
- 自动化定义、执行状态和历史持久化；
- 运行身份、防重复执行、恢复记录、投递结果与任务结果分开处理；
- 对不确定的外部写入不能盲目重放。

**需要修复或避免的短板**

- 主机工具默认高权限不适合 PA；
- 接入渠道数量不是产品价值；
- 定时任务如果直接唤醒模型，会造成成本、打扰和重复行动。

**PA 的选择**

先用本地条件评估和去重，再决定是否需要模型；渠道动作和外部副作用进入审批体系。

来源：[OpenClaw](https://github.com/openclaw/openclaw)、[Automations](https://docs.openclaw.ai/automation/cron-jobs)、[运行机制](https://docs.openclaw.ai/automation/cron-jobs/how-it-works)。

### 2.6 OpenFuse / OpenMuse：持久任务与后台工作

OpenMuse 官方链接当前转到 OpenFuse，本文按当前项目名记录，不把不同产品混写。

**值得借鉴**

- 任务计划、进度、等待输入、暂停、恢复、取消、重试、审批和收据；
- SQL lease 恢复中断工作；
- 周期性页面检查有去重提醒和失败退避；
- 浏览器可“Take control”，让用户接管；
- 不确定外部写入后不隐藏重试。

**需要避免**

- 默认依赖多个云服务；
- 将线程事实存放在不可控的外部服务；
- 把 Alpha 路线图当已经实现的能力。

**PA 的选择**

保留单进程、本地任务日志与本地恢复；浏览器和终端都是可中断工具，不是另一个 Agent。

来源：[OpenFuse](https://github.com/CopilotKit/openfuse)。

### 2.7 Obsidian 与 Basic Memory：本地 wiki 与人的可读性

**Obsidian 值得借鉴**

- 本地 Markdown、自由编辑、双链、反向链接和按人的习惯组织目录；
- 笔记不是只能被某个模型读取的私有格式。

**Basic Memory 值得借鉴**

- 文件是知识载体，数据库是重建得了的索引；
- 新文档中的 permalink 是稳定身份，移动和重命名不改变它；
- 文件夹主要服务人的浏览，关系来自内容；
- 锁定笔记可以阻止 AI 修改；
- 删除后保留未解析引用，能够发现断链；
- 索引可以重建，不必成为第二份真相。

**需要修复的短板**

- Obsidian 主要依赖人完成认知和维护；
- Basic Memory 的 project 是隔离知识库，关系默认不能跨 project；
- 默认从路径派生 permalink 仍不适合 PA 的所有资源；PA 从创建起就使用独立稳定 ID。

**PA 的选择**

跨项目保留统一记忆，以权限而不是文件夹决定可见性；日记和 wiki 的生成规则见 `docs/08`。

来源：[Basic Memory 知识格式](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)、[项目与文件夹](https://docs.basicmemory.com/raw/concepts/projects-and-folders.md)、[移动、删除与同步](https://docs.basicmemory.com/raw/local/user-guide.md)。

### 2.8 最终取舍

| 机制 | 默认内置 | 可扩展 | 不采用 |
|---|---:|---:|---:|
| 任务日志、停止、恢复、收据 | ✓ | | 靠模型口头报告任务状态 |
| diff、共同编辑、版本、撤销 | ✓ | 领域专用视图 | 整文件静默覆盖 |
| 多工作区、多根目录、资源重连 | ✓ | 新资源类型 | 路径即身份 |
| 学习、编程、文档能力 | ✓ | 新能力包 | 每领域独立 Agent |
| 场景 | ✓ | 用户分享场景包 | 场景隔离记忆 |
| 定时、到期和事件自动化 | ✓ | 新触发器与渠道 | 无预算的后台循环 |
| 多平台消息 | 基础渠道抽象 | 按需要接入 | 为数量而接入 |
| wiki、日记和长期记忆 | ✓ | 新视图 | 每句话生成一页 |

## 3. 统一概念：先把产品语言说一致

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Task | 一个有目标、状态、资源、行动、产物和验证的工作单元 | 一轮聊天 |
| Thread | 围绕任务的一种对话视图，可包含主线、侧问和分支 | 独立 Agent |
| Workspace | 一组资源根目录、权限和默认设置组成的工作范围 | 一个不可移动的文件夹 |
| Resource | 被使用的文件、教材、网页、仓库、消息或外部资料 | 一条绝对路径 |
| Resource Revision | 资源某一时刻的内容版本 | 每次打开都复制一份文件 |
| Artifact | 用户或 Agent 产出的可交付结果，如 diff、文档、表格、计划 | 一段声称已经完成的文字 |
| Capability | 工具、策略、验证器和展示方式的组合 | 一个新人格 |
| Mode | 用户保存的能力、默认模型、界面、权限和自动化组合 | 独立数据库或记忆空间 |
| Automation | 触发器、条件、任务、权限、预算和投递规则 | 到点无条件调用模型 |
| Channel | 消息输入输出适配器 | 另一份个人记忆 |
| Memory | 跨任务保留的经历、关系、理解和当前状态 | 当前上下文或聊天记录全文 |

这些对象之间是多对多关系：一个任务可使用多个工作区的资源；一个资源可参与多个任务；一个任务可有多个产物和对话视图。

## 4. 总体运行架构

```text
对话 / 编辑器 / wiki / 日程 / 消息渠道
                    │
                    ▼
          统一任务与执行内核
  目标 · 计划 · 行动 · 审批 · 停止 · 恢复 · 验证
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   能力组合       资源与产物      自动化运行
 学习/编程/工作   身份/版本/diff   触发/去重/投递
       │            │            │
       └────────────┼────────────┘
                    ▼
          上下文与长期记忆内核
   当前任务状态 / 原始经历 / wiki / 按需回忆
                    │
                    ▼
       本地运行与可替换基础设施
 SQLite · 文件 · Codex · 工具 · 模型 · 渠道
                    │
                    ▼
       权限、隐私、观测、成本贯穿所有层
```

### 4.1 三条状态不能混为一谈

1. **工作状态**：任务现在进行到哪一步，哪个动作等待审批，哪个文件正在被修改。
2. **工作上下文**：这一次模型实际看到的内容，压缩和截断只影响它。
3. **长期记忆**：从已经结束或有意义的经历中形成、可供未来使用的理解。

工作状态可以频繁变化；工作上下文可以丢弃和重建；长期记忆必须经过选择性写入和证据校验。

## 5. 统一任务与执行内核

### 5.1 一个任务必须携带什么

概念上，每个任务都能回答：

- 目标是什么，当前处于什么状态；
- 使用了哪些资源和历史决定；
- 当前计划是哪一版；
- 已执行哪些动作，各自结果是什么；
- 产生了哪些产物版本；
- 还缺什么输入或审批；
- 用什么证据证明完成、部分完成或失败；
- 消耗了多少模型、工具和时间预算；
- 哪些经历值得进入长期记忆。

任务可以跨对话、跨工作区、跨渠道和跨重启延续。

### 5.2 统一循环

```text
理解意图
→ 关联已有任务，避免重复开任务
→ 取得当前状态与必要记忆
→ 选择能力和资源
→ 制定或调整计划
→ 执行一个可观察动作
→ 记录动作与真实结果
→ 根据证据继续、等待、回滚或停止
→ 验证产物
→ 交付并保存值得保留的经历
```

### 5.3 状态语义

- **进行中**：正在执行或可以继续执行；
- **等待用户**：缺少只有用户能提供的信息；
- **等待审批**：下一步副作用需要授权；
- **部分完成**：有真实产物，但验收项未全部通过；
- **失败**：明确记录失败原因和已产生的副作用；
- **已取消**：停止后续动作，不假装之前动作未发生；
- **已完成**：该领域要求的验证证据齐全。

“等待审批”和“等待用户”不是失败；“模型没有回复”也不是任务完成。

### 5.4 停止、恢复与重试

- 每次运行有唯一身份和持久收据；
- 停止先阻止新动作，再尝试中止正在执行的工具；
- 重启后恢复任务状态，不自动重放有副作用的动作；
- 读取类动作可按策略重试；
- 外部写入结果未知时，状态必须是“结果未知”，先核对，不盲目重试；
- 模型重试、工具重试和整个任务重试是三种不同操作；
- 自动化和交互任务使用同一套收据语义。

### 5.5 证据式完成按领域定义

| 领域 | 可以接受的证据 | 不能算完成 |
|---|---|---|
| 编程 | diff、测试、构建、运行结果、截图或实际响应 | 只生成一个页面或声称测试通过 |
| 文档 | 文件真实存在、格式可打开、关键内容检查通过 | 只返回 Markdown 文案 |
| 学习 | 用户独立回答、teach-back、闭卷结果或后续复测 | Agent 说“你已经掌握” |
| 资料整理 | 资源清单、重复与断链报告、可重新定位的引用 | 只改标题或生成一份索引文档 |
| 决策 | 条件、选项、依据、预期和复盘时间被记录 | 给出一句笼统建议 |
| 外部行动 | 平台真实回执，且结果可核对 | 工具被调用就声称发送成功 |

## 6. 多工作区、资料库与路径无关身份

这是当前产品必须修复的基础问题，不是附加功能。

### 6.1 当前问题

当前 `books` 使用 `path/source_path`，`book_pages` 使用 `image_path`；Codex 和 CLI 产品也天然以 cwd 组织工作。如果把这些位置当作身份，会导致：

- 文件夹重命名后引用失效；
- 项目移动后历史无法定位；
- 一个任务被迫绑定一个文件夹；
- 多项目协作需要复制上下文；
- 导出到另一台机器后绝对路径全部失效；
- 原始文件、导入副本和解析页图容易分离。

### 6.2 身份、版本和位置分离

每个资源有三个完全不同的概念：

1. **资源身份**：创建时生成，终身稳定，不从路径计算；
2. **资源版本**：内容变化时产生新版本，引用可以锁定到版本；
3. **资源位置**：当前如何找到它，可以变化，也可以有多个候选位置。

路径只是位置，不是身份，也不是证据本身。

### 6.3 工作区由多个根目录组成

- 一个工作区可以挂载多个文件夹、多个磁盘和多个仓库；
- 一个资源也可以被多个工作区引用；
- 工作区本身有稳定身份，重命名不影响内部关系；
- 项目是组织和权限视图，不是记忆隔离墙；
- 工具执行时获得本次允许的根目录，而不是从任务历史反推 cwd；
- 切换 cwd 不切换任务，不重新绑定记忆。

### 6.4 移动、复制、修改和删除的语义

| 事件 | 系统行为 |
|---|---|
| 重命名 | 保留资源身份和全部版本，更新当前位置 |
| 移动 | 保留资源身份；更新位置历史；引用不变 |
| 内容修改 | 保留资源身份，产生新内容版本；使依赖旧内容的派生索引进入待更新状态 |
| 复制 | 默认建立新的资源身份，并记录“复制自”；不能因为 hash 相同就静默合并 |
| 替换 | 同一位置内容大变时给出版本差异；必要时请求用户确认是否仍是同一逻辑资源 |
| 暂时找不到 | 标记“断开”，不删除记忆，不自动当作遗忘 |
| 明确删除 | 删除位置和相应内容；派生数据按遗忘规则处理 |
| 导出迁移 | 导出稳定身份、内容版本和相对位置；机器相关的绝对位置单独保存 |

### 6.5 找不到以后怎样重连

按可信度使用多类线索：

1. 文件系统移动事件和位置历史；
2. 操作系统可提供时的卷与文件身份；
3. 已保存的内容版本指纹；
4. 文件名、大小、时间和目录结构等弱线索。

内容指纹相同只是候选证据，不自动证明“移动”而非“复制”。多个候选冲突时让用户选择，不能猜一个继续写。

### 6.6 引用不指向裸路径

长期引用指向：

> **资源身份 + 内容版本（需要时）+ 内部位置**

内部位置可以是页码、标题、选区、代码行范围或提交版本。绝对路径只在本次读取时由本地系统解析出来，不写入可迁移记忆正文。

### 6.7 原始资料、托管副本和派生物分开

- **外部挂载**：保留用户原文件，PA 不强制复制；
- **托管导入**：用户选择复制进 PA 数据根目录，原文件保留来源关系；
- **解析产物**：页文本、OCR、页图、提纲和索引属于可重建派生物；
- **生成产物**：用户与 Agent 创建的新版本，有独立版本历史；
- **记忆证据**：指向具体资源和版本，不把整份资料复制进记忆。

当前页图散落在工作区的问题，应通过“资源版本—派生物”关联修复，清理临时工作区不能误删唯一页图。

### 6.8 资料库整理不是换一批文件夹

资料库同时提供：

- 人的集合与文件夹视图；
- 自动主题、项目、学科、人物和时间视图；
- 精确重复、疑似重复、缺失、断开、无来源和过期报告；
- 教材、试卷、网页、代码仓库等不同解析策略；
- 文字层可靠性、缺图、扫描件和 OCR 状态；
- 用户确认的合并与拆分，可撤销。

外部资料内容一律作为数据，不作为系统指令。资料变化只更新相关索引和派生理解，不全库重新总结。

## 7. 统一编辑器与产物版本

### 7.1 一个编辑器模型，多种展示

代码 diff、文档修订、表格变化、学习计划 ChangeSet 和 wiki 更新，本质都包含：

- 基线版本；
- 提案版本；
- 可阅读的差异；
- 用户接受、拒绝或继续修改；
- 应用后的新版本；
- 可逆操作与审计。

不要求所有领域显示同一种文本 diff，但语义必须一致。

### 7.2 共同编辑规则

- Agent 的提案必须基于明确的基线版本；
- 用户可以直接修改提案，修改成为新的用户版本；
- Agent 后续工作以用户版本为新基线，不能继续覆盖旧提案；
- 外部程序同时修改资源时，先检测基线冲突，再请求合并或重新生成；
- 大块变更可以逐块接受，高风险变更默认不自动应用；
- 用户和 Agent 的修改在日志中明确区分。

### 7.3 所有写路径进入版本机制

不仅文本编辑工具：

- shell 或脚本写文件；
- 文档生成器；
- 浏览器下载；
- 图片与 PDF 处理；
- 计划应用；
- 自动化后台写入。

对可管理的工作根目录，在动作前建立必要快照；Git 可用时利用 Git，不存在 Git 时仍能进行应用级版本恢复。大文件可以采用内容分块或外部版本存储，不能为了快照无条件复制整个磁盘。

### 7.4 对话和产物分别恢复

用户应能选择：

- 只回到某个对话点，保留当前产物；
- 只恢复产物，保留当前讨论；
- 两者一起恢复；
- 从该点创建分支，保留原路径。

分支共享资源和记忆身份，但后续新经历分别记录，不能互相篡改。

### 7.5 编辑器是任务的一部分

编辑器中可以看到：

- 当前任务与目标；
- 正在编辑的版本；
- 相关原话、资料和历史决定；
- 变更来源；
- 验证结果；
- 后续动作。

关闭编辑器不应把任务状态变成一个无法继续的附件。

### 7.6 Intelligent UI 与交互组件

ChatGPT 在 2026-10 随 GPT-6 推出了 **Intelligent UI**：模型在聊天中生成图表、表单、计算器、迷你应用，由原生组件库和流式编译器边生成边渲染。

我们借这个方向，但只把它当作一层：

- **聊天内**：交互组件，让用户直接操作、回答、比较；
- **聊天外**：同样的内容可以落成文档、幻灯片、表格，进入查看器和版本系统。

Intelligent UI 不是让模型生成任意网页，而是让模型输出**声明式界面描述**，由本地应用渲染和接管。

它解决的问题：

- 纯 Markdown 只能读，不能答题、填表、对比、操作；
- 任意 HTML 难以审计、难以保证安全、容易出现“假页面”；
- 每次交互都靠自然语言来回，效率低。

**基本组件**

- 答题卡：单选、多选、填空、简答、判分、解析、回传；
- 表单：结构化输入、校验、提交；
- 表格：可编辑单元格、排序、过滤；
- 图表：折线、柱状、散点、时间线；
- 对比卡：选项、条件、预期、取舍；
- 代码 diff：逐块接受/拒绝；
- 文件预览：文档、PDF、图片、表格；
- 交互式数学/几何：参数调节、图形变化；
- 步骤卡：计划、进度、审批、恢复。

**组件契约**

每个组件必须声明：

- 数据来源；
- 当前状态；
- 可用动作；
- 动作的真实处理者；
- 回传给 Agent 的结构化结果；
- 失败和空状态。

**真实性要求**

- 答题卡的判分必须走真实判分逻辑，不能只显示“已判”；
- 表单提交必须写入真实状态；
- 图表必须绑定真实数据；
- 文件预览必须指向真实文件版本；
- 组件渲染失败时明确报错，不能伪装成成功。

**安全边界**

- 默认只允许白名单组件，不允许任意脚本；
- 需要自定义 HTML 时，放入沙箱 iframe，默认禁用脚本和网络；
- 外部内容一律作为数据，不作为指令；
- 组件不能自行扩大权限或调用未授权工具。

**降级**

无法渲染时退回 Markdown，并明确标注“交互组件不可用”，不生成一个看起来能用的假界面。

### 7.7 Office AI：Markdown 之上的真实文档

Office AI 不是每次生成一个网页，也不是复刻 Microsoft Office。

它是一层**内容 + 排版 + 渲染**：

```text
Markdown 内容
+ 样式与布局配置
+ 文档模板
→ 真实 DOCX / PPTX / XLSX / PDF
```

**文档模型**

- 内容块：标题、段落、列表、表格、图片、公式、代码、引用；
- 样式：字体、字号、粗细、颜色、行距、段距；
- 布局：对齐、居中、分栏、分页、页边距、页眉页脚；
- 模板：报告、履历、学习材料、幻灯片、表格；
- 变量：由数据或记忆填充，不把内容写死在模板里。

**渲染目标**

- DOCX：正式文档、作业、报告、履历；
- PPTX：演示、答辩、项目介绍；
- XLSX：表格、统计、计划；
- PDF：归档、打印、分享；
- HTML：仅作为预览或网页交付，不是默认产物。

**真实性要求**

- 生成后必须重新打开文件，检查页数、幻灯片数、单元格和关键内容；
- 文件不存在、打不开、内容缺失时，状态不能是已完成；
- 排版由渲染器执行，不能靠模型在文本里“假装居中”；
- 导出前检查是否含真实身份信息，按隐私规则处理。

**与 Intelligence UI 的关系**

- Office AI 负责“可交付文件”；
- Intelligence UI 负责“可交互界面”；
- 两者共享同一套内容、资源和版本，不是两个孤岛。

**先生成结构，本地渲染**

生成 Office 文件本身费时费力。默认路径不是先生成 DOCX/PPTX，而是：

```text
模型生成 PA 文档结构（比 Markdown 多排版语义）
→ 本地渲染器立即显示
→ 用户确认后再导出 DOCX/PPTX/XLSX/PDF
```

- 生成：模型负责内容与结构；
- 渲染：本地确定性渲染器负责显示；
- 导出：需要文件时才走 Office 渲染；
- 对话里能快速看到接近最终排版的效果，又不必每次付出生成 Office 的成本。

**用户编辑**

- 用户可以在应用内改内容或排版；
- 也可以导出后在 Office 中继续改；
- 再次导入时保留来源和版本，不把用户修改覆盖掉。

### 7.8 内置查看器：完成的证据面

如果没有查看器，Agent 说“文档写好了”，用户却打不开、看不到，就仍然等于假完成。

查看器不是附件预览，而是**产物真实性的检查面**。

**必须内置的查看器**

| 查看器 | 支持 | 关键能力 |
|---|---|---|
| 文档 | Markdown、DOCX、PDF、HTML | 目录、翻页/滚动、缩放、搜索、批注、导出 |
| 表格 | XLSX、CSV | 网格、公式、筛选、图表、多工作表 |
| 幻灯片 | PPTX | 缩略图、全屏、演讲者备注、导出 |
| 图片 / PDF | PNG、JPG、PDF | 缩放、页缩略图、OCR 文字层、标注 |
| 代码 / diff | 文本、补丁 | 语法高亮、逐块接受/拒绝、行号 |
| 网页 | 生成的 HTML | 沙箱预览，默认禁脚本和网络 |
| 数据 / 图表 | 表格、JSON | 绑定真实数据，不画假图 |
| 记忆 / wiki | 页面、双链 | 来源、版本、反链、证据 |
| 对比 | 两个版本或两份文件 | 并排、差异高亮 |

**真实性要求**

- 查看器绑定的是**资源身份 + 版本**，不是模型临时生成的字符串；
- 打开时显示来源、版本、修改者和时间；
- 文件不存在、格式损坏、内容缺失时明确报错；
- DOCX/PPTX/XLSX 必须用真实解析或转换，不能只显示文件名；
- 页面/幻灯片/单元格数量与文件实际一致；
- 查看器打不开时，任务状态不能是“已完成”。

**与完成判定的关系**

```text
Agent 声称完成
→ 文件存在
→ 查看器成功打开
→ 关键内容检查通过
→ 才能标记完成
```

**外部打开与保真**

- 提供“用系统应用打开”入口；
- 复杂排版、字体、公式、图表要标注保真风险；
- 导出前做一次真实打开检查，不只检查文件大小。

**编辑闭环**

- 查看器可以直接编辑内容或排版；
- 保存产生新版本，保留来源；
- 用户在外部应用修改后重新导入，不能被旧版本覆盖。

**阅读游标与未读状态**

查看器要记住用户看到哪里：

- 每条消息、文档、幻灯片按块记录已读范围；
- 打开时恢复上次位置；
- 显示未读分隔线；
- Agent 只拿到“已读至 X、未读 Y”的摘要，不接收原始滚动事件；
- 用户回滚不会把后面的块误标为已读；
- 未读内容可以要求 Agent 重说，或从这里继续；
- 阅读状态本地保存，默认不上传云端。

## 8. 能力包与场景

### 8.1 能力包的组成

每种能力由四部分组成：

1. **工具**：能做什么；
2. **策略**：何时使用、什么不该做；
3. **验证器**：怎样判断结果真实完成；
4. **展示投影**：结果在对话和编辑器中怎样呈现。

学习、编程、文档和决策只是不同组合，不复制任务、权限、记忆和版本系统。

### 8.2 场景是一份可版本化的组合

场景可以定义：

- 常用能力和默认资源；
- 默认模型与预算；
- 界面布局；
- 常用提示与工作流；
- 记忆的默认召回范围与写入偏好；
- 自动化与免打扰规则；
- 在全局权限以内的默认审批策略。

场景不能：

- 绕过全局安全边界；
- 创建另一份不可互通的记忆；
- 把已有任务强行改名或重绑目录；
- 让每次切换都重放全部系统提示和历史。

### 8.3 学习是示例场景，不是产品定义

作者自己的学习场景由通用机制组合：

- 九科与体育能力；
- 教材、真题和训练资源视图；
- 讲解、侧问、闭卷检查与复习验证器；
- 今日计划、待复测和学习 wiki 布局；
- 复习到期、晚间复盘和赛事冲突提醒；
- 作者自己的语言、成本、隐私与情绪安全偏好。

其他用户可以创建写作、创业、研究或完全不同的场景；内核不需要新增“学习特判”。

场景之间共享任务、资源和记忆；跨场景任务通过实体、目标、时间冲突和明确引用连接。

### 8.4 场景分享与扩展安全

场景包可以分享配置、技能、资源视图和展示方式，但安装时必须展示：

- 新增工具；
- 读写范围；
- 网络与渠道权限；
- 自动化行为；
- 数据出口。

社区场景不能因“只是一个 Markdown 配置”就获得隐式执行权限。

## 9. 上下文、记忆与缓存

### 9.1 上下文装配顺序

稳定部分与动态部分分开：

```text
稳定核心规则与当前能力
→ 当前任务的持久状态
→ 最近必要历史或交接摘要
→ 本次按需召回的记忆与资料
→ 用户当前输入
```

动态记忆和检索结果放在尾部，避免每轮重写稳定前缀。

### 9.2 压缩不等于记忆

- 压缩服务当前任务的继续；
- 压缩摘要必须标明是模型生成的交接，不是用户原话；
- 原始事件仍可回查；
- 压缩不能切断工具调用与结果；
- 长期记忆另走选择性写入和 Dreaming；
- 清空上下文不自动清空任务、资源和长期记忆。

### 9.3 中文任务不强制英文推理

- 系统指令、工具说明和动态上下文默认中文；
- 工具名只是机器标识，不要求模型用英文组织自然语言；
- 不主动插入“中文→英文思考→中文回答”的额外步骤；
- 输出语言跟随用户与场景，代码标识符保持合适语言；
- 模型内部不可见的计算过程不作虚假承诺，产品能控制的是不强制英文提示和额外翻译；
- 通过中文任务探针检查工具选择、回答语言和成本，而不是只看提示词写得是否中文。

---

## 10. 主动行为与多平台通信

### 10.1 主动行为由事件驱动，不由心跳聊天驱动

触发器包括：

- 用户手动运行；
- 一次性时间与周期计划；
- 复习、决策复盘和承诺到期；
- 资源变化；
- 新消息；
- 外部页面或条件的用户授权监测；
- 任务等待或失败状态。

本地条件先判断是否需要行动，只有确实需要理解、生成或决策时才调用模型。

### 10.2 每次自动化都包含

- 触发条件与错过的触发如何处理；
- 唯一运行身份；
- 去重键和冷却时间；
- 预算、超时和最大动作数；
- 权限与审批策略；
- 免打扰和汇总投递；
- 运行收据、结果和失败原因；
- 用户暂停、取消和修改入口。

### 10.3 自主程度分级

1. **提醒**：只告诉用户发生了什么；
2. **建议**：给出建议，不生成外部副作用；
3. **草拟**：生成文档或消息草稿，等待用户确认；
4. **单次批准行动**：本次明确授权后执行；
5. **有限长期授权**：只在明确范围、频率和预算内行动，随时可撤销。

默认不能从“定时提醒”自动升级成“定时替用户发消息”。

### 10.4 多平台通信原则

- 渠道只负责传输、身份认证和平台能力适配；
- 外部消息默认不可信，不直接成为系统指令；
- 同一真人跨渠道的关联需要明确配对或用户确认，不靠昵称猜测；
- 对话可以跨渠道继续同一任务；
- 发送、修改日历、公开回复等外向动作需要相应审批；
- 渠道限流、平台失败和投递未知必须可见；
- 渠道内容进入长期记忆前仍经过隐私和选择性写入。

## 11. 产品信息架构

### 11.1 主界面不是功能大卖场

默认保持白底、简洁和对话优先：

- 中间：当前任务与对话；
- 左侧：进行中的任务、计划和可切换工作视图；
- 右侧：按任务出现的编辑器、diff、资料、记忆、验证和审批；
- 顶栏：模型、费用、权限和运行状态；
- 工具过程默认折叠为一句摘要，需要时展开。

### 11.2 视图随任务出现

| 任务 | 主要辅助视图 |
|---|---|
| 学习 | 教材页、讲解、题目、待复测、学习计划 |
| 编程 | 文件、diff、测试、命令、诊断 |
| 文档 | 页面预览、修订、素材、导出 |
| 决策 | 类似经历、选项、预期、复盘 |
| 资料整理 | 重复、断开、元数据、来源和引用 |
| 自动化 | 条件、下次运行、历史收据、免打扰 |
| 通信 | 会话、渠道、身份、待审批草稿 |

这些不是互相隔离的应用模式，而是同一任务的不同侧面。

### 11.3 用户始终能回答四个问题

1. 它现在在做什么？
2. 它为什么这样做？
3. 它改了什么、花了多少？
4. 我怎样停止、撤销、纠正或忘掉？

## 12. 权限、隐私与可观测性

### 12.1 权限按动作而不是按“Agent 很可信”划分

至少区分：

- 本地读取；
- 本地写入；
- 进程执行；
- 网络读取；
- 外部服务写入；
- 消息发送；
- 自动化长期授权。

能力包和场景只能缩小或请求权限，不能静默扩大。

### 12.2 隐私边界

- 原始数据默认本地；
- 云端请求有出站检查；
- 真实身份与稳定代号映射分离；
- 记忆、wiki、索引和向量只保存代号；
- 真名替换只发生在本地查看器、最终导出和用户明确授权的界面；
- 替换后的真名不得回传给云端模型；
- off-the-record 不进入长期事件、索引和自动化；
- 删除覆盖派生摘要、wiki、索引和缓存；
- 外部导出文件和云提供商保留策略必须单独说明，不能承诺本地删除就能收回所有副本。

详细规则见记忆架构。

### 12.3 Inspector 是核心功能

每次任务都能检查：

- 实际模型与路由；
- 实际提示上下文和记忆命中；
- 使用了哪些资源版本；
- 工具参数、结果、审批和副作用；
- 产物版本与验证证据；
- token、缓存、人民币成本和耗时；
- 自动化触发与渠道投递。

隐私视图可以脱敏，但不能为了“简洁”隐藏实际执行事实。

## 13. 对现有实现的复用与改造地图

### 13.1 继续复用

- `pa-app` 单进程入口；
- 进程内 Codex app-server / core；
- `codex-study` 与同一 SQLite；
- 现有流式对话、停止、线程、图片、工具记录和 usage；
- 学习、跑步、教材、文档解析与导出工具中已验证的部分；
- ChangeSet 的计划修改思想。

### 13.2 改造而不是另起产品

| 当前实现 | 需要演进为 |
|---|---|
| global / subject thread | 共享任务与记忆的对话视图，不再承担隔离边界 |
| `memory_docs` | 可迁移的旧式笔记，进入新记忆体系，不继续作为唯一长期记忆 |
| books 的路径字段 | 稳定资源身份、内容版本与可变位置 |
| uploads / imports 分散文件 | 外部资源、托管副本和派生物的明确关系 |
| 学习 ChangeSet | 通用产物提案与应用语义 |
| 学习工具集 | 通用能力注册中的一种能力包 |
| 首轮固定文档注入 | 当前任务状态 + 按需 Recall + 缓存友好的尾部装配 |
| 学习界面 | 随任务变化的通用工作视图 |
| 手动操作 | 同一任务内核驱动的交互与自动化运行 |

### 13.3 数据迁移原则

- 不删除现有数据库和文件；
- 原绝对路径成为初始位置，不作为新身份；
- 旧 memory docs 作为有来源的历史笔记，不逐句自动升级为事实；
- 迁移可重复执行、可回滚、有数量与引用核对；
- 新系统未通过验收前，旧数据保持可读。

## 14. 跨领域闭环示例

### 14.1 学习与资料

```text
用户问“这里为什么”
→ 找到教材资源与具体版本、页码
→ 识别当前任务与过去误解
→ 更换讲解方式
→ 用户完成独立检查
→ 更新学习状态
→ 生成或更新待复测
→ 到期由自动化提醒
```

教材移动后，页码引用仍然指向同一资源版本。

### 14.2 编程

```text
用户要求修复
→ 任务关联仓库与相关历史决定
→ 读取当前版本并提出计划
→ 生成可审查 diff
→ 用户修改其中一块
→ 以用户版本继续
→ shell 测试产生真实结果
→ 失败则保留失败状态并继续修复
→ 交付 diff、测试和剩余风险
→ 保存值得长期保留的架构决策
```

### 14.3 文档与决策

```text
读取多份资料
→ 形成有来源的比较
→ 生成真实文档
→ 用户与 Agent 共同修订
→ 记录选择、预期和复盘时间
→ 到期召回当时预期与实际结果
```

### 14.4 跨域：比赛与学习冲突

Agent 同时读取：

- 当前学习任务和考试目标；
- 比赛资料与真实时间；
- 过去类似活动的预期、结果和形成的决策原则；
- 当前项目机会与需要产出的 Demo。

输出不是一句“建议去/不去”，而是有条件的建议、计划 ChangeSet 和待复盘决定。它使用的是同一个 Agent 的学习、文档、项目与记忆能力。

### 14.5 跨渠道主动复盘

到期后，本地自动化发现需要复盘：

- 在免打扰时间内只生成待处理提醒；
- 用户选择渠道后发送草稿或请求回复；
- 用户回复进入同一决策任务；
- 结果形成新的经历，而不是另一条孤立通知。

## 15. 验收设计

以下测试都应在真实 `pa-app` 和数据副本上执行，不以静态页面代替。

### 15.1 任务与证据

- 编程任务未跑测试时，状态不能是已完成；
- 文档任务必须重新打开真实产物并检查内容；
- 工具结果未知时不能重放外部写入；
- 停止、重启、恢复后任务状态和副作用记录一致。

### 15.2 多工作区与资源

- 同一任务挂载两个不同目录的资源，无需复制到新项目；
- 重命名工作区和根目录后，历史引用仍能打开；
- 移动教材后，页码引用、学习记录和记忆仍指向原资源；
- 复制同一文件不会被误判为移动并静默合并；
- 多候选重连时必须请求用户选择；
- 导出到另一目录或机器后，可以通过相对位置或重连恢复；
- 清理临时目录不会删除唯一页图或唯一解析证据。

### 15.3 编辑与版本

- 用户可以逐块接受和拒绝；
- 用户修改 Agent 提案后，后续生成以用户版本为基线；
- 外部并发修改不会被静默覆盖；
- 编辑工具和 shell 产生的修改都能进入恢复机制；
- 对话与产物可以独立恢复和创建分支。

### 15.4 场景与跨域

- 从学习场景创建编程任务，不需要重新介绍用户目标；
- 两种模式看到相同的授权记忆与资源，但有不同界面和默认能力；
- 场景不能扩大权限；
- 用户创建的新模式不需要修改通用内核。

### 15.5 主动行为与渠道

- 同一触发不会重复生成多条提醒；
- 免打扰时不会擅自发送；
- 重启不会重复执行已完成的外部动作；
- 结果未知的外部写入不会被盲目重试；
- 未配对渠道消息不能调用高权限工具；
- 用户可撤销长期自动化授权。

### 15.6 中文与透明

- 中文任务不出现人为添加的英文推理或中英往返步骤；
- 工具说明中文化后，中文探针的工具选择不退化；
- 每轮可查看真实模型、上下文、资源、记忆、工具、缓存和成本。

### 15.7 Intelligent UI、Office AI 与查看器

- 答题卡、表单、图表等组件必须连接真实处理逻辑；
- 组件动作失败时状态可见，不能伪装成功；
- 任意 HTML 默认沙箱化，禁止脚本和网络；
- 文档、幻灯片、表格生成后必须能被内置查看器打开；
- 页数、幻灯片数、工作表和关键内容与文件实际一致；
- 查看器打不开、格式损坏、内容缺失时，任务不能标记完成；
- 导出文件能用系统应用打开一次；
- 云端请求中不出现真名、地址、电话、学校或公司；
- 本地查看器和导出能正确替换代号，替换后不回传模型。

## 16. 经济模型

### 16.1 成本公式

所有能力统一按真实模型调用计费：

```text
月成本 =
普通任务模型调用
+ 动态记忆与资料上下文
+ Dreaming
+ 自动化模型调用
+ 多平台理解与生成
+ 文档/图片等额外处理
```

单次调用成本为：

```text
缓存输入 token × 缓存价格
+ 非缓存输入 token × 输入价格
+ 输出 token × 输出价格
```

工具循环意味着“一个用户轮次”可能包含多次模型调用，成本预算必须按**模型调用**记录，不能只数用户消息。

### 16.2 记忆相关的参考容量

沿用记忆文档中的保守假设：5000 用户轮次/月、每轮一次普通模型调用、500 个待整理经历，采用项目现有人民币费率卡。

| 项目 | 高峰估算 | 非高峰估算 |
|---|---:|---:|
| 普通负载，含动态记忆与 Dreaming | ¥72.592/月 | ¥36.296/月 |
| 重负载，含动态记忆与 Dreaming | ¥165.592/月 | ¥82.796/月 |

这些是容量估算，不是实测账单，也不是完整通用 Agent 的成本上限。工具多轮、图片、浏览器、自动化和多渠道需要另加真实调用。

### 16.3 成本控制机制

- 每个任务有模型调用、输出 token 和自动化频率预算；
- 本地条件评估先于模型；
- 稳定前缀与动态尾部提高缓存命中；
- 只更新受影响的记忆和 wiki；
- 自动化失败退避，不因错误反复调用模型；
- 每月按任务、能力、记忆、自动化和渠道分解成本；
- 接近预算时提示用户调整，不静默换模型。

## 17. 明确不采用的架构

- 以当前文件夹作为任务、资源和记忆的唯一身份；
- 每种能力一个数据库、一套权限和一份用户画像；
- 先把所有功能做成插件，基础安全再交给社区；
- 每晚把所有历史重新总结一次；
- 定时器到点就直接把整份画像发给模型；
- 对话、代码和文档各自维护无法对齐的撤销历史；
- 用向量搜索代替证据、时间和任务状态；
- 用竞品功能数量衡量通用性；
- 用“页面看起来完成”代替领域验证证据。

---

## 18. 总体架构是否成立的判断标准

这套架构只有在以下条件同时满足时才成立：

1. 用户可以在多个项目目录之间工作，而不用担心移动和重命名；
2. 学习、编程、文档和决策共享任务、资源和记忆；
3. 用户创造新模式时，不需要开发一个新 Agent；
4. 编辑器中的每次变化有基线、来源、版本和验证；
5. 主动行为和多平台通信不会绕开权限与任务状态；
6. 记忆可以更新、解释、纠错和遗忘；
7. 中文路径不被人为翻译成英文工作流；
8. 成本能按真实调用拆分并控制；
9. 跨域任务不需要用户手动搬运上下文；
10. 系统没有把任何未实现能力写成已完成。

**这就是“融为一炉”的具体含义：不是功能在同一窗口出现，而是它们共享同一套事实、状态、历史和控制权。**
