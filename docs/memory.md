## 0. 核心判断

记忆系统不是把聊天历史压缩得越来越短，也不是让模型维护越来越多的 Markdown 文件。

它应该模仿一个认真生活、但不需要手工整理所有资料的人：

1. **随手记录**：保存对话、行动、文件和自己的想法；
2. **形成经历**：知道一件事的起因、行动、结果和当时理解；
3. **定期复盘**：新结果改变对旧经历的解释，但不篡改当时原话；
4. **沉淀 wiki**：把人物、项目、主题和当前状态组织成可读页面；
5. **按需回忆**：在未来任务中取出少量相关经历、证据和不确定性；
6. **纠正与遗忘**：用户可以改变理解，也可以真正删除不希望继续存在的内容。

因此，完整结构是：

```text
原始事件与资料
      │
      ▼
经历、实体、主张、意向、决定、模式
      │
      ├──────────────► 日记 / 复盘 / wiki / 人物志
      │                  （可重建的人读视图）
      │
      └──────────────► 按需 Recall
                         （供当前任务使用的小证据包）
```

**wiki 不是 Recall 的必经步骤，也不是记忆本体；它是记忆网络的一种投影。**

### 0.1 三个不能混淆的系统

| 系统 | 回答的问题 | 生命周期 |
|---|---|---|
| 工作状态 | 当前任务进行到哪里、下一步是什么 | 高频变化，任务完成后归档 |
| 工作上下文 | 这次模型实际看到什么 | 可压缩、截断、重建 |
| 长期记忆 | 哪些经历和理解对以后仍有价值 | 有选择地保留、更新、纠错和遗忘 |

压缩对话不是长期记忆，保存任务状态也不是个人理解。

## 1. 设计原则

1. **原始证据优先**：任何派生结论都能回到原话、工具结果、文件版本或用户明确操作。
2. **用户内容不被模型静默改写**：模型只能追加解释和新版本；用户真正的删除例外。
3. **选择性记忆**：默认 no-op，不把每句话变成页面和人格标签。
4. **当前与历史共存**：旧结论失效不等于从历史中消失。
5. **事实、观点和推断分开**：用户自述、外部资料、工具观察和模型推断具有不同证明力。
6. **模式是条件化假设**：必须寻找反例，不制造永久人格标签。
7. **日记与 wiki 可编辑**：用户修改成为新的用户证据或用户 authored 内容，不被下一次 Dreaming 覆盖。
8. **本地与模型无关**：更换模型不改变稳定身份、证据和导出格式。
9. **遗忘是一等操作**：删除派生理解、索引、视图和缓存，不是只隐藏一条记录。
10. **成本有界**：只处理新增和受影响的内容，不做全历史 nightly 重算。

## 2. 从人的笔记习惯到机器结构

### 2.1 日记、复盘、wiki 各自负责什么

| 形态 | 主要内容 | 更新方式 | 不是 |
|---|---|---|---|
| 日记 | 今天发生了什么、我做了什么、当时怎么想 | 按时间追加，可引用当天事件 | 当前事实数据库 |
| 复盘 | 结果如何、预期是否实现、理解为何变化 | 新证据到来时追加新版本 | 对旧日记的改写 |
| 主题 wiki | 某人物、项目、学科或主题当前怎样、有哪些关键历史 | 从网络重建，保留用户部分 | 原始资料复制仓库 |
| 人物志 | 当前阶段、目标、偏好、能力、决策方式及不确定性 | 从有效主张和模式重建 | 固定人格测评 |
| Recall 包 | 当前任务需要的一小段经历、结论和证据 | 每次按需生成 | 整份人物志 |

### 2.2 不采用“日→周→月→年逐级覆盖”的真相模型

日、周、月、年视图可以从较低层证据组织，但不能只拿上一段摘要继续摘要，形成“摘要的摘要的摘要”。

- 周复盘可以引用本周事件；
- 月度回顾应能回到相关经历和决定，而不是只读四份周摘要；
- 年度叙事应能重新检索全年关键事件、变化和反证；
- 原始事件不会因为生成了年度总结就自动删除；
- 用户选择精简存储时是明确的归档或遗忘操作，不是视图生成的副作用。

多级视图是**不同粒度的阅读方式**，不是多级有损压缩的唯一真相链。

## 3. 记忆网络的六类对象

旧稿的 Episode、Entity、Claim、Pattern 不足以表达目标、承诺和复盘。新版使用六类对象。

### 3.1 Episode：一段有边界的经历

一段经历包含：

- 发生了什么；
- 谁以什么角色参与；
- 用户、Agent 或工具做了什么；
- 结果是什么；
- 当时怎样理解；
- 对应哪些原始事件和资源版本。

一段对话可以包含多个 Episode；一个 Episode 也可以跨多个对话视图和渠道。边界通常来自：

- 一个任务开始与结束；
- 一个明确决定及其结果；
- 一次学习、会议、合作或训练；
- 主题发生实质变化；
- 用户明确标记；
- 导入材料中可识别的事件区间。

Episode 保存证据引用和派生概括，不复制整段原文。

### 3.2 Entity：连接经历的对象

包括人、组织、项目、地点、学科、概念和其他需要长期追踪的对象。

- 身份稳定，不随名字和路径变化；
- 别名和真实身份映射在本地管理；
- 角色和关系具有时间范围；
- 同名不能作为自动合并的充分条件；
- 合并和拆分都可撤销，历史引用随关系修正。

文件和仓库首先属于总体架构中的 Resource；需要讨论“这个项目”时，可由 Entity 与 Resource 建立关系，避免把资源身份和概念身份混为一谈。

### 3.3 Claim：一条可判断真假的理解

Claim 是原子命题，例如：

- “某次机会评估中，用户表示更看重行业连接而非奖金。”
- “某项目在某一时间处于进行中。”
- “用户在项目机会评估中曾担心挤占核心目标时间。”

每条 Claim 都具有：

- 适用对象与范围；
- 来源视角；
- 支持与反驳证据；
- 有效时间与获知时间；
- 确认状态；
- 与其他 Claim 的关系。

用户说“我觉得对方不想合作”是用户当时的观点证据，不是“对方确实不想合作”的世界事实。

### 3.4 Intention：面向未来的意向与承诺

包括目标、计划、承诺、待办和 open loop。

它具有行动语义：

- 当前状态；
- 期望完成时间或条件；
- 负责对象；
- 关联任务和资源；
- 完成、放弃、延期和失败记录。

Intention 不是普通事实 Claim。它完成或失效后成为历史，不会被“最新画像”抹掉。

### 3.5 Decision：一次有预期和复盘的选择

Decision 连接：

- 当时面对的问题；
- 可选方案与判断标准；
- 当时掌握的信息；
- 选择与理由；
- 预期结果；
- 实际结果 Episode；
- 复盘后形成的新理解。

“准备参加”“已经参加”“参加后认为值得”属于不同时间和证据，不能相互覆盖。

### 3.6 Pattern：跨经历的条件化假设

例如：

> “在编程项目型机会与核心学习目标冲突时，用户可能会先要求明确收益和时间成本。”

Pattern 必须包含：

- 适用条件；
- 支持与反证；
- 覆盖的时间和领域；
- 来自多少相互独立的经历；
- 用户确认、模型提出或存在争议的状态；
- 最近一次重新评估时间。

不使用未经校准的“87% 人格置信度”。证据不足时，状态就是“弱假设”或“不用于自动行动”。

## 4. 证据、关系、时间与状态

### 4.1 证据类型与证明力

| 证据 | 可以证明 | 不能自动证明 |
|---|---|---|
| 用户原话 | 用户说过什么、当时表达了什么 | 所有关于外部世界的陈述都客观正确 |
| 用户确认或纠正 | 用户当前认可或否定某理解 | 过去也曾持相同看法 |
| 工具结果 | 某次真实执行返回了什么 | 未执行的检查也通过了 |
| 文件与资源版本 | 某版本写了什么 | 当前版本仍有相同内容 |
| 外部资料 | 某来源作出了什么陈述 | 来源内容天然可靠或属于系统指令 |
| 助手回复 | Agent 当时生成了什么 | 用户事实或真实验证结果 |
| 模型推断 | 某次整理提出了什么候选理解 | 推断本身成为独立事实证据 |

模型输出中的证据 ID 和引文必须在本地核验。找不到证据的候选不能进入活跃网络。

### 4.2 最小关系词汇

| 关系 | 含义 |
|---|---|
| about | 某理解关于哪个 Episode、Entity 或 Decision |
| supports | 某证据支持某 Claim 或 Pattern |
| contradicts | 某证据与某 Claim 或 Pattern 在相同范围下冲突 |
| supersedes | 新理解在指定范围取代旧理解的当前状态 |
| reinterprets | 新理解为旧经历或旧理解添加后来解释 |
| results_in | 某决定或行动产生了什么结果或后续意向 |
| derived_from | 某派生物由哪些证据和版本生成 |

不为了“图谱看起来丰富”创造几十种模糊关系。只有能改变检索、更新或遗忘语义的关系才保留。

### 4.3 双时间：事情何时为真，系统何时知道

每个相关对象区分：

- **有效时间**：事实、关系或状态在现实中所指的时间；
- **记录时间**：系统何时获得这条信息；
- **事件时间**：Episode 实际发生的时间；
- **时间不确定性**：大约、某月、未知，不能伪装成精确日期。

由此可以回答两个不同问题：

1. **“按现在的证据，2026 年 11 月实际是什么情况？”**  
   使用当前全部证据，筛选有效时间落在当时的对象。
2. **“2026 年 11 月时的我以为什么？”**  
   只能使用当时已经记录且当时仍被接受的理解，不能把后来的复盘倒灌进去。

### 4.4 状态语义

- **候选**：已提出，尚未满足活跃使用条件；
- **活跃**：可在适用范围内参与 Recall；
- **被取代**：不再是当前理解，但保留历史；
- **有争议**：同范围存在尚未解决的冲突；
- **已否定**：用户或可靠证据否定了它；
- **已遗忘**：按用户要求删除，不再参与任何生成和推断。

“被取代”和“已遗忘”完全不同。

## 5. 写入：从原始事件到记忆网络

### 5.1 在线只做必要工作

正常模式下，原始消息、工具结果、产物版本和用户动作先进入本地事件记录。在线路径负责：

- 隐私与 off-the-record 边界；
- 任务和 Episode 的关联；
- 必要的稳定身份；
- 明确的“记住”请求；
- 不阻塞当前对话的轻量候选入队。

不是每轮都调用模型重写人物志。

### 5.2 Episode 整理

当一个经历形成边界时，DeepSeek 在有限输入内提出候选：

- 是否值得长期保留；
- 发生了哪些关键变化；
- 涉及哪些实体；
- 有哪些用户明确表达、工具事实和结果；
- 是否产生意向或决定；
- 哪些引文和资源位置支持这些候选。

**空结果是正常且优先的结果。** 闲聊、重复确认、临时界面状态和已被资源本身表达的内容不进入活跃网络。

### 5.3 本地验证先于写入

代码必须检查：

- 引文是否真实存在；
- 证据是否属于允许的隐私范围；
- 时间是否被无依据地精确化；
- 用户陈述是否被误写成客观事实；
- 工具结果是否被夸大；
- 资源版本是否存在；
- 实体合并是否有足够依据；
- 写入是否重复或已处理过。

模型负责提出候选，代码没有义务接受。

### 5.4 关联已有网络

候选入口来自：

- 明确任务和实体关系；
- 本地全文检索；
- 时间和资源引用；
- 可选的语义向量召回。

初始实现可采用“最多 20 个候选入口，核验后最多 10 个交给模型比较”的有界预算。这个数值是工程初值，不是架构真理，后续用评测调整。

模型只提出“重复、补充、支持、反驳、取代或重释”的判断，最终写入仍通过本地约束。

### 5.5 更新规则

| 新情况 | 正确处理 |
|---|---|
| 同一事实的新证据 | 给现有 Claim 增加证据，不新建重复页面 |
| 同一范围下更精确的信息 | 产生新版本，明确哪些范围被取代 |
| 不同时间的不同状态 | 分别保留有效时间，不视为矛盾 |
| 同时间、同范围的真实冲突 | 标记争议并保留双方证据，不能“最新永远赢” |
| 用户纠正模型理解 | 新增高优先级用户证据，否定或取代相应派生 Claim |
| 后来结果改变旧事件意义 | 新增 reinterprets，不改写当时预期 |
| 实体改名 | 添加别名，保留身份 |
| 两个实体误合并 | 执行可撤销拆分，重新分配证据与视图 |
| 外部资料更新 | 新资源版本触发相关 Claim 复核，不全库重写 |
| 证据消失但仍有其他支持 | 重新计算支持和视图，Claim 可保留 |
| 最后一条有效证据被删除 | 派生 Claim 失效或删除，不能继续作为事实使用 |

### 5.6 Pattern 的形成与退休

只有满足以下条件才提出 Pattern：

- 不是单段话的同义重复；
- 有跨 Episode 的支持；
- 已主动检索过反例；
- 适用条件可以被说清；
- 新理解对未来任务有实际用途。

高影响自我理解、敏感属性和用于自动行动的 Pattern 需要用户确认。新反例可以降低使用范围、标记争议或退休，不能把反例静默吞掉。

## 6. Dreaming：后台维护，不是整夜重写人生

### 6.1 工作队列由变化驱动

以下事件产生有界工作项：

- 新 Episode 待整理；
- 新证据可能影响旧 Claim；
- 新冲突或反例；
- Decision 到期复盘；
- 资源版本变化；
- 用户编辑、合并或拆分；
- 证据遗忘；
- wiki 页面过期或断链；
- 用户手动请求重建。

没有变化时可以不调用模型。

### 6.2 一次运行的边界

一次 Dreaming 工作项只处理：

- 一个新 Episode，或
- 一个受影响的局部网络，或
- 一个到期的决定，或
- 一组相关视图。

初始批量上限可设为 10 个新 Episode；关联只读取有界候选，wiki 只重建受影响页面。预算不足时保留待办，不通过扩大上下文硬跑。

### 6.3 幂等与单写者

- 工作项绑定输入证据版本，重复运行不能生成重复记忆；
- 输入已变化时，旧结果不能覆盖新版本；
- 同一页面或同一局部网络只有一个写入者；
- 失败保留明确状态，不静默当作成功；
- 每个生成结果都有 derivation 记录；
- 回滚是恢复派生版本，不伪造原始历史。

### 6.4 离线整理与在线召回分离

Dreaming 未完成时：

- 原始事件仍然可查；
- 当前任务状态仍然可用；
- 已确认的旧记忆仍可按时间使用；
- 新候选明确标为未整理；
- 不为了等待画像而阻塞聊天。

## 7. Recall：从问题出发重建，而不是 top-k 事实拼盘

### 7.1 先判断是否需要长期记忆

当前任务状态、用户刚提供的材料和明确资源引用优先。简单闲聊、当前消息已经回答的问题，不应强行召回个人历史。

需要长期记忆时，先解析：

- 用户问的是现在、过去还是当时认知；
- 涉及哪些实体、任务和时间；
- 是要事实、类似经历、决定理由、证据还是表达风格；
- 当前隐私范围允许使用什么。

### 7.2 入口检索与有界扩展

```text
当前任务 / 明确实体 / 全文与可选语义搜索 / 时间入口
→ 找到 Episode、Entity、Claim、Intention 或 Decision
→ 按问题类型沿必要关系扩展
→ 应用时间、隐私和证据过滤
→ 检查支持与反证
→ 取回关键原文或资源片段
→ 组装小型 Recall 包
```

初始遍历任一入口最多扩展两层；只有用户继续追问或证据不足时才深化。图数据库不是必需条件，SQLite 中的关系和本地文件足以实现逻辑遍历。

### 7.3 不同问题使用不同遍历规则

| 问题 | 优先入口 | 必要扩展 |
|---|---|---|
| 我最近在做什么 | 活跃 Intention 和任务 | 最近 Episode、相关项目、待决定事项 |
| 我当时怎么想 | 指定时间的 Episode 和当时记录 | 当时已知 Claim，排除后来重释 |
| 类似事情后来怎样 | 相似 Episode 与 Decision | 预期、实际结果、复盘、后续原则 |
| 为什么做那个决定 | Decision | 当时证据、选项、标准、结果 |
| 写我的履历 | 已核验的项目和成果 Episode | 资源版本、真实产物、时间和角色 |
| 帮我回复某人 | 当前对象与场景 | 同场景用户原话、关系边界、近期事件 |
| 我现在喜欢什么 | 当前有效偏好 Claim | 反例、适用条件、最近纠正 |
| 某资料讲了什么 | Resource 与 Revision | 页码、选区和来源，不走人格网络 |

### 7.4 排序先做硬过滤，再谈相关度

先排除：

- 不在隐私范围内的内容；
- 不符合时间语义的内容；
- 已遗忘内容；
- 无有效证据的候选；
- 已被取代且问题只问当前状态的内容；
- 与任务无关的敏感信息。

然后综合任务相关性、证据质量、时间接近性和覆盖程度选择。Recency 不能自动战胜用户纠正和明确反证。

### 7.5 Recall 包的内容

默认预算可从每轮约 1200 token 开始，重任务可提高但有硬上限。包内只放：

- 当前有效且直接相关的理解；
- 必要的经历和结果；
- 关键反例或争议；
- 时间位置；
- 可回查的证据引用；
- 明确的信息缺口。

不默认放整份人物志、全部关系和不相关敏感历史。

### 7.6 回答与拒答

- 事实性回答尽可能带可检查来源；
- 模型推断必须使用推断语气；
- 有实质冲突时呈现冲突，不编造统一答案；
- 找不到足够证据时明确说“不知道”或“现有记录只能证明……”；
- 用户问当时认知时，不能利用后来的信息塑造一个更聪明的过去自己。

## 8. 日记、wiki 与人物志怎样生成和编辑

### 8.1 页面类型有上限，不为每条 Claim 建页

默认只有几类有用视图：

- 按日期的日记；
- 人物、组织、项目、学科和主题页；
- Decision 与复盘页；
- 当前人物志；
- 必要的索引和时间线。

只有当一个对象有独立阅读或召回需要时才建页。相似内容优先合并到现有页，wiki 规模不能随消息数线性增长。

阅读形态可以参考 Obsidian：双链、反向链接、局部关系图、用户自由编辑。区别是链接由认知网络生成，用户不必手工维护；用户手写内容单独保存，不被重建覆盖。

### 8.2 页面生成规则

每页从明确对象出发：

1. 读取当前有效理解与必要历史；
2. 检查支持、反证和争议；
3. 按时间组织关键 Episode；
4. 区分用户原话、事实、模型解释和信息缺口；
5. 附上证据链接；
6. 记录本页来源版本；
7. 只在相关输入变化时重建。

页面是地图，不是把原始语料换一种格式复制一遍。

### 8.3 用户编辑不能被覆盖

页面内容分为三类：

- **用户 authored 部分**：只能由用户修改，可锁定；
- **Agent 生成部分**：可以从网络重建；
- **用户对 Agent 结论的纠正**：成为新的用户证据，影响后续生成。

用户修改生成句时，不应简单把整页标记为“永远不可重建”，而应把修改保存为用户覆盖或纠正，再重建其余部分。

### 8.4 合并、拆分、断链和回滚

- 页面合并保存来源关系，可撤销；
- 页面拆分不复制出多份相同证据；
- 删除页面留下可发现的未解析链接，不能静默制造假引用；
- 每次生成有版本，可回到旧视图；
- 回滚视图不删除新证据，之后仍可重新生成最新视图。

### 8.5 人物志不是一份越来越长的文档

当前人物志只包含：

- 当前阶段与活跃目标；
- 已核验的能力和经历；
- 有证据的偏好与决策方式；
- 重要反例和不确定性；
- 信息缺口。

详细经历留在项目页、主题页和 Episode 中。历史人物志由时间切片重建，不靠保留无数份全文副本。

## 9. 隐私、身份与 off-the-record

### 9.1 原始身份与云端身份分离

- 原始证据和真实别名映射保存在本地；
- 云端处理使用稳定代号，保证跨次请求仍能关联同一实体；
- 记忆正文、wiki、索引和向量只保存代号，不保存真名、地址、电话、学校或公司；
- 真名替换只发生在本地查看器、最终导出和用户明确授权的界面；
- 前端替换后的真名不得回传给云端模型；
- 本地 UI 和最终导出可以按权限恢复真实身份；
- 代号映射、密钥和真实身份不进入普通 wiki 正文；
- 路径、文件名、附件、日志和错误信息也进入出站检查。

### 9.2 off-the-record 的硬边界

off-the-record 内容不得进入：

- 长期事件记录；
- Episode 和 Claim；
- Dreaming 队列；
- 全文和向量索引；
- wiki 与人物志；
- 自动化条件；
- 本地持久 prompt 快照和恢复日志。

当前临时上下文只用于本次明确允许的计算，并尽可能减少工具副作用。云提供商自己的传输和保留策略不受本地开关控制，界面必须如实说明；高度敏感内容需要本地模型或不发送。

### 9.3 第三方信息

- 只保存任务所需内容；
- 标明是谁的说法和是否核实；
- 不因为某人与某公司有关，就把公司的行为归到个人；
- 不把情绪和推测写成事实；
- 不因当前任务方便，就把敏感第三方信息扩展到无关场景。

## 10. 真正遗忘

### 10.1 三种用户意图必须分开

1. **不再用于当前画像**：可以 retired 或限定范围，但保留历史；
2. **纠正过去理解**：新增纠正和取代关系，保留可审计历史；
3. **彻底忘掉**：删除指定证据及其不再受支持的派生内容。

用户说“忘掉这个”默认应理解为第三种，而不是仅把条目隐藏。

### 10.2 删除依赖处理

删除证据后：

- 检查所有由它支持的 Claim 和 Pattern；
- 有其他独立支持的，重新生成并保留；
- 失去最后有效证据的，删除或使其不再可用；
- 重建受影响的日记、wiki、人物志和时间视图；
- 清理全文、向量、召回缓存、prompt 派生副本和待处理队列；
- 处理指向删除内容的链接，不能留下仍可展开原文的假引用；
- 审计只保留不含被删内容的操作收据。

### 10.3 资源断开不等于遗忘

文件暂时移动或找不到时，只标记断开。用户必须区分：

- 删除资源位置；
- 删除资源内容；
- 删除与资源相关的长期记忆；
- 保留关于这段经历的记忆，但删除原始附件。

不能一次文件移动就自动抹掉一段人生经历。

### 10.4 遗忘的诚实边界

- 已导出到 PA 之外的文件无法由本地删除自动收回；
- 旧备份需要通过删除传播、加密密钥策略或备份轮换处理，界面要说明；
- 云提供商已经接收的数据受其保留策略约束，本地删除不能承诺收回；
- 因此默认最小化上传、身份代号化和 off-the-record 比事后删除更重要。

## 11. 导出、迁移与旧记忆处理

### 11.1 开放导出

导出包含：

- Markdown 日记、wiki 和人物志；
- 结构化经历、关系、时间和版本；
- 证据与资源清单；
- 稳定身份和相对位置；
- 用户 authored 内容与模型派生内容的区别；
- 必要的重建信息。

导出不要求接收方使用同一个模型或同一个数据库。

### 11.2 现有 `memory_docs` 迁移

当前实现按 name 覆盖文档，没有证据、版本和时间语义。迁移时：

- 每份旧文档作为一个有名称和更新时间的 legacy note；
- 保留原文，不逐句自动升级为已确认事实；
- 可以对其提出候选 Claim，但标明来源限制；
- 用户确认后进入活跃网络；
- 新旧系统并行核对，不删除旧文档；
- 迁移可重复执行且可回滚。

## 12. DeepSeek 与确定性代码的责任边界

| DeepSeek 可以做 | 代码必须保证 |
|---|---|
| 判断候选是否值得整理 | off-the-record 和权限边界 |
| 划分候选 Episode | 原始事件与资源引用存在 |
| 抽取 Entity、Claim、Intention、Decision | 引文、时间、来源视角和写入幂等 |
| 提议重复、支持、冲突、取代和重释 | 不允许无证据覆盖当前状态 |
| 提议 Pattern | 反例检索、状态和用户确认规则 |
| 生成日记、wiki 和人物志草稿 | 版本、单写者、来源和回滚 |
| 协助组织 Recall 结果 | 时间过滤、隐私、预算和证据完整性 |
| 对不确定问题作出候选解释 | 无证据时必须允许拒答 |

DeepSeek 不需要自主维护一个无限增长的目录。模型看到的是局部任务和有限候选，代码维护身份、状态、事务和版本。

## 13. 经济账

### 13.1 价格与口径

采用项目现有人民币费率卡：

| 费率 | 高峰 | 非高峰 |
|---|---:|---:|
| 非缓存输入 / 百万 token | ¥2.00 | ¥1.00 |
| 缓存输入 / 百万 token | ¥0.04 | ¥0.02 |
| 输出 / 百万 token | ¥8.00 | ¥4.00 |

这是当前代码费率卡下的容量估算，不是对 2026-11-21 官方价格的重新核验，也不是实测账单。

### 13.2 正常负载假设

- 5000 用户轮次/月，每轮一次普通模型调用；
- 每轮 20k 缓存前缀、1.5k 普通新输入、700 输出；
- 动态记忆平均每轮 1.2k，按非缓存输入保守计价；
- 500 个 Episode/月；
- 每个 Episode 抽取：6k 输入、400 输出；
- 每个 Episode 关联：3k 输入、200 输出；
- 定向 Pattern 与 wiki 维护预算：每月额外 0.36M 输入、0.184M 输出。

普通对话：

```text
缓存：20,000 × 0.04 / 1,000,000 = ¥0.0008 / 轮
新输入：1,500 × 2 / 1,000,000 = ¥0.003 / 轮
输出：700 × 8 / 1,000,000 = ¥0.0056 / 轮
合计：¥0.0094 × 5000 = ¥47.00 / 月
```

动态记忆：

```text
1,200 × 2 / 1,000,000 × 5000 = ¥12.00 / 月
```

Dreaming：

```text
Episode 抽取：
500 × (6,000 × 2/M + 400 × 8/M) = ¥7.60

Episode 关联：
500 × (3,000 × 2/M + 200 × 8/M) = ¥3.80

定向 Pattern 与 wiki：
0.36M × 2/M + 0.184M × 8/M = ¥2.192

Dreaming 合计：¥13.592 / 月
```

正常负载总计：

> **¥47.00 + ¥12.00 + ¥13.592 = ¥72.592 高峰；¥36.296 非高峰。**

### 13.3 重负载假设

每轮 60k 缓存、5k 普通新输入、3k 动态记忆、1.5k 输出，Dreaming 不变：

```text
普通对话：¥122.00
动态记忆：¥30.00
Dreaming：¥13.592
```

> **总计 ¥165.592 高峰；¥82.796 非高峰。**

### 13.4 这套估算没有包含什么

- 一个用户轮次中的多次工具循环模型调用；
- 图片、长文档和浏览器任务；
- 多平台与自动化额外模型调用；
- 向重模型升级；
- 缓存失效和失败重试。

因此预算控制必须按真实 usage 分解，而不能拿 ¥72.592 当所有使用方式的包月承诺。通用 Agent 的补充成本规则见总体架构。

## 14. 验证方案

### 14.1 一个跨时间例子

**第一次对话：计划**

用户说更看重行业连接而非奖金，同时担心活动挤占核心目标时间。

系统形成：

- 一个计划参加活动的 Intention；
- 两条用户自述 Claim；
- 一个可能涉及的 Decision，保留当时信息和预期。

此时不能形成“用户总是重视人脉”的 Pattern。

**几天后：参加**

用户说认识了一个团队，但其他任务堆积。

系统形成实际参加 Episode 和时间成本结果。它说明这次活动出现了什么，**不能单凭一次结果证明稳定人格偏好**。

**两个月后：复盘**

用户说合作没有继续，但 Demo 得到有用反馈，并形成“活动前先明确目标”的原则。

系统：

- 记录实际结果；
- 给旧预期增加后来解释；
- 不篡改当时的期待；
- 形成用户明确提出的决策原则；
- 将更一般的 Pattern 保持为弱假设，并寻找反例。

**又过两个月：应用**

用户在新比赛中主动引用该原则。

系统增加一条独立 Episode，Pattern 可以升级为“有用户确认、在机会评估领域有重复证据”，仍不能推广为所有人生决策。

**一年后提问**

- “我现在怎样做这类决定？”：返回当前原则和适用条件；
- “当时的我怎么想？”：只返回当时已经记录的重视连接与担心时间，不倒灌后来的原则；
- “哪次经历让你这样判断？”：返回三次关键 Episode 和原话；
- “这个原则有没有失败过？”：必须检索反例；没有记录时说没有记录，不声称从未失败。

### 14.2 必须通过的确定性测试

- 每条活跃 Claim 都有可解析的有效证据；
- 模型伪造的证据引用会被拒绝；
- off-the-record 在所有长期存储、索引和队列中均无记录；
- 用户纠正后，当前问题不再返回旧结论；
- 当时问题仍能返回历史理解；
- 同范围冲突不会被最新内容静默覆盖；
- 删除最后证据后，派生 Claim 不可检索、不可从 wiki 推断；
- 共享其他证据的 Claim 在删除后仍能正确重建；
- 用户 authored wiki 内容不会被 Dreaming 覆盖；
- 实体合并与拆分可撤销；
- 导出后更换模型不需要重新生成原始证据；
- 重复 Dreaming 不产生重复 Claim 和页面。

这些测试应全部通过，不用平均分掩盖隐私或遗忘失败。

### 14.3 模型质量探针

建立 30–50 个中文个人问题，覆盖 LongMemEval 的五类能力：

- 信息提取；
- 多经历推理；
- 知识更新；
- 时间推理；
- 无证据拒答。

再加入 PA 特有题型：

- 类似经历的结果与反例；
- 履历的真实证据；
- 用户沟通风格与场景条件；
- 资源版本和页码引用；
- 用户编辑与否定；
- 不相关记忆污染；
- 文档膨胀与 no-op。

报告事实准确率、引用准确率、时间错误率、过时回答率、拒答正确率、无关注入率、每百 Episode 页面增长、延迟和成本。与“无长期记忆”和“只全文搜索”两个基线比较，不能只展示成功演示。

## 15. 架构不变量

1. 原始事件与派生理解分开；
2. Episode 不等于整条对话；
3. Intention 和 Decision 不被硬塞成普通事实；
4. 当前状态变化不篡改历史；
5. 用户纠正优先于模型自信；
6. Pattern 必须有条件、反证和退休机制；
7. wiki 是可重建视图，用户 authored 内容不可被覆盖；
8. Recall 先确定时间与问题类型，再遍历和取证；
9. 没有证据时允许不记、不答和不确定；
10. 遗忘沿证据依赖处理所有派生副本；
11. 资源位置变化不改变记忆身份；
12. 模型更换不改变用户数据所有权；
13. Dreaming 只处理变化和受影响局部；
14. 成本按真实模型调用核算；
15. 任何“形成了理解”的说法都必须能展示证据链和通过相应探针。

> **这套系统的核心不是让 AI 永远记住一切，而是让人和 AI 的共同经历能够被保存、被理解、被重新解释，也能够在用户决定时被真正放下。**
